## Совместимость с текущим фронтендом

Всё добавлено так, чтобы текущий фронтенд продолжал работать без изменений:

- новые поля в ответах только добавляются (`role` у участника, `paidBy` у расхода, `recurring` у платежа…);
- все, кто входит по обычному коду семьи, — взрослые (`parent`), как и раньше;
- ограничения ребёнка действуют только для участников с ролью `child`, которых сейчас нет.

## 1. Роли в семье

**Зачем.** Взрослые управляют деньгами семьи, ребёнок видит только свои карманные деньги и может попросить покупку.

### Правила

- Роли: `parent` (взрослый) и `child` (ребёнок).
- Создатель семьи и все, кто вошёл по коду семьи (`inviteCode`), — `parent`.
- Ребёнок входит только по **детскому приглашению**: одноразовый код, выдаёт взрослый, действует 7 дней,
  активных — не больше 5 на семью. Тот, кто войдёт по нему, получит роль `child`, сам выбрать роль нельзя.
- Взрослый может сменить роль любого участника и исключить любого участника, кроме себя.
- В семье всегда есть хотя бы один взрослый: нельзя понизить последнего взрослого, а последний взрослый
  не может выйти, пока в семье есть другие участники («сначала назначьте другого взрослого»).
- Исключённый участник теряет все сессии; его записи остаются семье с прежним автором.
- **Ребёнок не получает код семьи**: в `family.inviteCode` для него `null` (в `/family`, `/state` и в ответе
  на вход). По коду семьи входят с правами взрослого — иначе ребёнок мог бы войти заново взрослым или
  переслать код постороннему.

### Что видит и может ребёнок

| Действие | Ребёнок |
|---|---|
| Состав семьи, свои расходы, свои запросы, цели, свои уведомления | ✅ |
| Добавлять, менять, удалять свои расходы — в пределах карманных денег | ✅ |
| Менять расход, созданный по его одобренному запросу | ❌ 403 (это может взрослый) |
| Создавать и отменять свои запросы на покупку, вносить в цели | ✅ |
| Бюджет, платежи, чужие расходы, сводка, проверка покупки, прогноз, расчёты между взрослыми | ❌ 403 |
| Приглашения, роли, исключение, карманные деньги, импорт выписки, создание целей | ❌ 403 |

`GET /state` для ребёнка отдаёт только разрешённое: `budgets: []`, `payments: []`, в `expenses` — только свои.
Сообщение 403: «Это доступно только взрослым участникам семьи».

### API

| Метод и путь | Кто | Тело → ответ |
|---|---|---|
| `POST /family/child-invites` | взрослый | — → `201 {code, expiresAt}` |
| `GET /invites/{code}` | все | ответ дополнен полем `role`: `parent` для кода семьи, `child` для детского |
| `POST /invites/{code}/join` | все | как раньше; по детскому коду участник получает `role: child`, код гасится |
| `PUT /family/members/{id}` | взрослый | `{role}` → `200 Family` |
| `DELETE /family/members/{id}` | взрослый | → `204` |

Участник в ответах: `{id, name, color, role}`.

Ошибки: `403` — не взрослый; `404` — нет участника; `409` — последний взрослый, лимит детских приглашений;
`422` — себя исключить нельзя (для этого есть `POST /family/leave`).

## 2. Карманные деньги

**Зачем.** Ребёнок учится распоряжаться деньгами в понятных рамках, родители видят, на что они уходят.

### Правила

- Карманные деньги — **лимит трат ребёнка** на период: неделя (пн–вс) или календарный месяц, в поясе `TIMEZONE`.
- Назначает и меняет взрослый; только для участника с ролью `child`.
- Траты ребёнка — это обычные расходы семьи: они входят в «Потрачено» семейного бюджета по своей категории.
  Сама сумма карманных денег расходом не является, поэтому двойного учёта нет.
- «Потрачено из карманных» за период = расходы ребёнка (кроме созданных одобренным запросом, §3)
  + его взносы в цели (§4) за этот период.
- Ребёнок может добавить расход, только если:
  - карманные деньги назначены (иначе `403` «Карманные деньги не назначены — отправьте запрос на покупку»);
  - дата расхода — в текущем периоде и не в будущем (иначе `422 date`): нельзя «спрятать» трату в прошлый период;
  - хватает остатка (иначе `422 amount` «Не хватает карманных денег: осталось N ₽»).
- Те же проверки — при изменении расхода (учитывается разница сумм).

### API

| Метод и путь | Кто | Тело → ответ |
|---|---|---|
| `PUT /family/members/{id}/allowance` | взрослый | `{amount, period: "week" \| "month"}` → `200 Allowance` |
| `DELETE /family/members/{id}/allowance` | взрослый | → `204` |
| `GET /allowances` | все | взрослый — по всем детям, ребёнок — свой → `[Allowance]` |

```ts
Allowance = {
  memberId: string; amount: number; period: "week" | "month";
  periodStart: "YYYY-MM-DD"; periodEnd: "YYYY-MM-DD";   // включительно
  spent: number; left: number; updatedAt: number
}
```

`GET /state` дополнен полем `allowances` (тот же состав, что `GET /allowances`).

## 3. Запросы на покупку

**Зачем.** «Можно купить?» превращается в один тап: просящий видит ответ, взрослый — готовый расчёт.

### Правила

- Создаёт любой участник; ожидающих запросов у одного автора — не больше 20.
- Решение принимает **взрослый, не являющийся автором** (взрослый не одобряет сам себе).
- Статусы: `pending` → `approved` | `rejected` (решение взрослого) или `cancelled` (автор отменил).
  Решённый запрос не меняется.
- При одобрении создаётся расход: автор — тот, кто просил, «оплатил» — одобривший взрослый (§7),
  дата — сегодня, `requestId` — запрос. Такой расход **не** уменьшает карманные деньги ребёнка.
- Взрослые видят все запросы семьи, ребёнок — только свои.
- Для взрослых каждый ожидающий запрос содержит `check` — проверку покупки на текущий месяц
  (как `POST /months/{month}/purchase-check`). Ребёнку `check` не отдаётся: это данные о бюджете семьи.
- Одновременные решения двух взрослых: строка запроса блокируется, выигрывает первый, второй получит `409`.

### API

| Метод и путь | Кто | Тело → ответ |
|---|---|---|
| `POST /purchase-requests` | все, **идемпотентный** | `{title, amount, category, comment?}` → `201 PurchaseRequest` |
| `GET /purchase-requests?status=` | все | → `[PurchaseRequest]`, новые сверху |
| `POST /purchase-requests/{id}/approve` | взрослый, не автор | `{comment?}` → `200 PurchaseRequest` (с `expenseId`) |
| `POST /purchase-requests/{id}/reject` | взрослый, не автор | `{comment?}` → `200 PurchaseRequest` |
| `POST /purchase-requests/{id}/cancel` | автор | → `200 PurchaseRequest` |

```ts
PurchaseRequest = {
  id; familyId; authorId; title; amount; category; comment: string | null;
  status: "pending" | "approved" | "rejected" | "cancelled";
  decidedBy: string | null; decidedAt: number | null; decisionComment: string | null;
  expenseId: string | null; createdAt: number;
  check?: PurchaseCheck        // только взрослым и только для pending
}
```

`comment` и `decisionComment` — до 300 символов.

## 4. Цели-копилки

**Зачем.** Семья копит на общее (отпуск, велосипед) и видит, успевает ли к сроку.

### Правила

- Создаёт, меняет и архивирует цель взрослый; вносить может любой участник (ребёнок — из карманных денег, §2).
- Цель: название (≤ 80), сумма > 0, срок (необязательно). Активных целей — не больше 20.
- Когда накоплено ≥ цели, статус становится `achieved` (всем участникам — уведомление, §9). Удаление взноса
  может вернуть цель в `active`.
- Взнос — в активную или достигнутую цель; в архивную — нельзя. Удалить взнос может только его автор.
- Цель без взносов можно удалить, со взносами — только архивировать.
- Взносы **не** входят в формулы бюджета (это не трата, а откладывание). В сводке месяца — отдельное
  справочное поле `savedThisMonth`.
- Прогноз: средний взнос в месяц за последние 3 месяца с первого взноса → `etaMonth` (месяц достижения);
  при сроке — `monthlyNeeded`, сколько откладывать в месяц, чтобы успеть.

### API

| Метод и путь | Кто | Тело → ответ |
|---|---|---|
| `GET /goals` | все | → `[Goal]`: активные и достигнутые, затем архивные |
| `POST /goals` | взрослый, **идемпотентный** | `{title, target, deadline?}` → `201 Goal` |
| `PUT /goals/{id}` | взрослый | `{title, target, deadline?}` → `200 Goal` |
| `POST /goals/{id}/archive` | взрослый | → `200 Goal` |
| `DELETE /goals/{id}` | взрослый | → `204`; `409`, если есть взносы |
| `GET /goals/{id}/contributions` | все | → `[Contribution]`, новые сверху |
| `POST /goals/{id}/contributions` | все, **идемпотентный** | `{amount, date?}` → `201 {goal, contribution}` |
| `DELETE /goals/{id}/contributions/{cid}` | автор взноса | → `200 Goal` |

```ts
Goal = {
  id; familyId; title; target: number; deadline: string | null;
  status: "active" | "achieved" | "archived";
  saved: number; left: number; percent: number;          // percent 0–100, округлено вниз
  monthlyNeeded: number | null; etaMonth: "YYYY-MM" | null;
  createdBy; createdAt: number; achievedAt: number | null
}
Contribution = { id; goalId; memberId; amount; date; createdAt }
```

## 5. Прогноз на конец месяца

**Зачем.** Понять заранее, а не 30-го числа, что семья выходит за план.

### Правила

- «Обязательные» траты — расходы, созданные отметкой платежа, и ещё не оплаченные платежи месяца.
  «Текущие» — все остальные расходы.
- Текущий месяц: средний расход в день = текущие траты / прошедшие дни (включая сегодня);
  прогноз текущих = текущие + средний × оставшиеся дни; прогноз всего = прогноз текущих + обязательные.
- Прошлый месяц: прогноз = факт. Будущий: прогноз = неоплаченные платежи.
- `lowConfidence: true`, если прошло меньше 5 дней — средняя ещё ненадёжна.
- По категориям — тот же расчёт; `status: "over"`, если прогноз выше лимита категории.

### API

`GET /months/{month}/forecast` — взрослый.

```ts
Forecast = {
  monthKey; kind: "past" | "current" | "future"; plan; spent; reserved;
  variableSpent; dailyAverage; daysPassed; daysInMonth;
  projectedSpent; projectedLeft;          // план − прогноз; < 0 — превышение
  lowConfidence: boolean;
  categories: [{ key; plan; spent; projected; status: "ok" | "over" | "no-limit" }]
}
```

## 6. Повторяющиеся платежи

**Зачем.** Аренда, садик, связь каждый месяц появляются сами.

### Правила

- При создании платежа можно указать `recurring: true`. Платёж становится началом **серии**.
- Сервер держит в серии платежи на текущий и следующий месяц: создаёт недостающие при создании платежа
  и фоновой задачей (раз в час). Новый платёж серии — копия последнего (название, сумма, категория),
  день месяца сохраняется (31-е в коротком месяце → последний день), статус `upcoming`.
- Изменение суммы или названия одного платежа меняет только его; следующие копируются с последнего.
- `PUT /payments/{id}` с `recurring: false` останавливает серию: уже созданные платежи остаются.
- Защита от дублей: в серии один платёж на месяц (уникальный индекс), поэтому несколько копий backend
  не создадут лишнего.
- Перенос из прошлого месяца (`copy-previous-month`) пропускает платежи серий — они уже есть.
- Дату платежа серии можно менять только в пределах его месяца (`422 dueDate`) — в серии один платёж на месяц.
- Остановить серию можно через любой её **неоплаченный** платёж (оплаченные не редактируются).
- Если серию давно не продлевали, за один проход создаётся не больше 12 месяцев.

### API

`POST /payments` и `PUT /payments/{id}` принимают необязательное поле `recurring: boolean`.
В `Payment` добавлены `recurring: boolean` и `seriesId: string | null`.

## 7. Кто кому должен

**Зачем.** В спецификации «кто внёс расход — не обязательно тот, кто платил». Семья видит, кто сколько
потратил из своих и как выровнять.

### Правила

- У расхода появляется `paidBy` — кто платил. По умолчанию — автор; при оплате платежа — кто отметил;
  при одобрении запроса — одобривший взрослый.
- Взрослый может указать платившим любого текущего взрослого семьи; ребёнок — только себя.
- Общие траты месяца — расходы, оплаченные взрослыми (траты ребёнка из карманных не делятся).
  Делятся поровну между взрослыми: текущими и вышедшими, если они платили в этом месяце.
  Копейки остатка распределяются по одной детерминированно (по порядку вступления).
- Баланс = заплатил − доля + переведено − получено; > 0 — ему должны.
- Переводы — минимальный набор «кто → кому → сколько», жадно от наибольших долгов.
- Отметить, что перевод сделан: `POST /months/{month}/settlements`; это меняет балансы. Удалить отметку может её автор.
  Отправитель и получатель — текущие взрослые семьи, разные; ответ обоих методов — пересчитанный `Settlement`.

### API

| Метод и путь | Кто | Тело → ответ |
|---|---|---|
| `POST /expenses`, `PUT /expenses/{id}` | — | необязательное поле `paidBy` |
| `GET /months/{month}/settlement` | взрослый | → `Settlement` |
| `POST /months/{month}/settlements` | взрослый | `{fromId, toId, amount}` → `201 Settlement` |
| `DELETE /months/{month}/settlements/{id}` | автор отметки | → `200 Settlement` |

```ts
Settlement = {
  monthKey; sharedTotal: number;
  members: [{ memberId; name; paid; share; sent; received; balance }];
  transfers: [{ fromId; toId; amount }];          // что осталось перевести
  recorded: [{ id; fromId; toId; amount; createdBy; createdAt }]
}
```

## 8. QR-код чека

**Зачем.** Расход заносится за секунду: навести камеру на чек.

### Правила

- QR российского кассового чека — строка вида `t=20261021T1530&s=1250.50&fn=…&i=…&fp=…&n=1`.
  Разбирается на сервере без обращения к ФНС: сумма `s`, дата и время `t`, фискальные реквизиты `fn`, `i`, `fp`.
- Один чек — один расход в семье: повтор того же чека → `409` (`field: receipt`, «Этот чек уже добавлен»).
  Узнать, какой расход уже создан по чеку, — `POST /receipts/parse` (`duplicateOf`; ребёнку — только
  для его собственных расходов, иначе `null`).
- Фискальные реквизиты не хранятся — только SHA-256 от `fn:i:fp`.
- Сумма расхода может отличаться от суммы чека (например, занесли часть покупок).

### API

| Метод и путь | Кто | Тело → ответ |
|---|---|---|
| `POST /receipts/parse` | все | `{qr}` → `{amount, date, time, duplicate: boolean, duplicateOf: string \| null}` |
| `POST /expenses` | — | необязательное поле `receipt` (строка QR, ≤ 512 символов) |

Ошибки разбора: `422 field: qr` «Не похоже на QR-код кассового чека».

## 9. Уведомления

**Зачем.** Не пропустить платёж, превышение лимита и просьбы детей.

### События

| `kind` | Кому | Когда |
|---|---|---|
| `payment_due` | взрослым | платёж не оплачен, срок сегодня–через 2 дня (один раз на платёж и дату) |
| `category_limit` | взрослым, кроме автора расхода | категория перешла в «почти исчерпан» или «превышен» (раз в месяц на статус) |
| `request_created` | взрослым, кроме автора | новый запрос на покупку |
| `request_decided` | автору запроса | запрос одобрен или отклонён |
| `goal_achieved` | всем | цель накоплена |
| `member_joined` | всем, кроме вошедшего | новый участник |
| `allowance_changed` | ребёнку | назначены или изменены карманные деньги |

Уведомление: `{id, kind, title, body, data, createdAt, readAt}`; `data` — id связанных объектов.
Хранятся 90 дней. Каждое событие также приходит в поток `/events` как `changed`.

### E-mail

- Участник может указать e-mail и включить отправку уведомлений на него.
- Адрес подтверждается 6-значным кодом из письма (`secrets`): код действует 15 минут, 5 попыток на код;
  хранится только HMAC-хеш, сравнение за постоянное время. Неподтверждённый адрес писем с уведомлениями
  не получает — так через сервис нельзя рассылать письма на чужие адреса.
- Адрес проверяется строгим шаблоном (без пробелов и переводов строк), домен приводится к нижнему регистру.
  Заголовки писем собирает `EmailMessage` — подставить свой заголовок через данные нельзя.
- Письма уходят через очередь (`email_outbox`) фоновой задачей; транспорт — SMTP (`SMTP_*`) или `EMAIL_BACKEND=outbox`
  (только очередь в базе — для разработки и тестов).
- Смена адреса — не чаще 5 раз в час. При выходе или исключении из семьи адрес удаляется.

### API

| Метод и путь | Кто | Тело → ответ |
|---|---|---|
| `GET /notifications?unreadOnly=&before=` | все | → `[Notification]`, до 50, новые сверху; `before` — `createdAt` для следующей страницы |
| `POST /notifications/{id}/read` | получатель | → `204` |
| `POST /notifications/read-all` | все | → `204` |
| `GET /me` | все | → `{id, name, role, email, emailVerified, notifyByEmail, pendingEmail, vtbLinked}` |
| `PUT /me/email` | все | `{email}` → `202` (письмо с кодом отправлено) |
| `POST /me/email/verify` | все | `{code}` → `200 Me` |
| `DELETE /me/email` | все | → `204` |
| `PUT /me/notifications` | все | `{email: boolean}` → `200 Me` |

`GET /state` дополнен `unreadNotifications: number`.

Переменные окружения: `EMAIL_BACKEND` (`outbox` | `smtp`), `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`,
`SMTP_FROM`, `SMTP_STARTTLS`, `EMAIL_SEND_INTERVAL_SECONDS`, `NOTIFICATION_TTL_DAYS` — см. [OPERATIONS.md](OPERATIONS.md).
Письмо отправляется до 5 раз с интервалом прохода очереди; несколько копий backend разбирают очередь
без дублей (`SELECT … FOR UPDATE SKIP LOCKED`).

## 10. Импорт выписки

**Зачем.** Не переписывать траты руками: загрузить выписку, проверить категории, подтвердить.

### Правила

- Загружает взрослый. Файл — CSV (UTF-8), разделитель `;` `,` или табуляция, первая строка — заголовки.
  Распознаются колонки (без учёта регистра):

  | Смысл | Варианты заголовка |
  |---|---|
  | Дата | `Дата`, `Дата операции`, `date` |
  | Сумма | `Сумма`, `Сумма операции`, `amount` |
  | Описание | `Описание`, `Назначение`, `Описание операции`, `description` |
  | MCC (необязательно) | `MCC`, `mcc` |

  Дата — `ДД.ММ.ГГГГ` или `ГГГГ-ММ-ДД`; сумма — с запятой или точкой; трата — отрицательная сумма,
  поступления (положительные) пропускаются.
- До 1000 строк и 1 МБ. Ожидающих подтверждения импортов — не больше 5 на семью, через 7 дней они удаляются.
- Категория предлагается по порядку: правила семьи (запомненные исправления) → MCC → ключевые слова → «Другое».
- Дубли: строка, уже импортированная в эту семью раньше (та же дата, сумма, описание и порядковый номер
  среди одинаковых строк файла), помечается `duplicate` и не импортируется.
- Ничего не попадает в расходы до подтверждения. При подтверждении можно поменять категорию и исключить строки;
  исправленные категории запоминаются как правила семьи.
- Строка с ошибкой (нет даты, неверная сумма) остаётся в импорте с `error` и не импортируется.
- Описание очищается от управляющих и невидимых символов и обрезается до 120 символов — становится названием расхода.
- Подтверждение блокирует импорт: повторное (вторая вкладка, двойной клик) получает `409`, расходы не дублируются;
  дополнительно расходы уникальны по отпечатку строки в семье.
- Тело `POST /imports` — до 2 МБ (единственное исключение из общего лимита 64 КБ, в backend и nginx);
  сам CSV — до 1 МБ. Поступления в базе не сохраняются вовсе — только их количество.

### API

| Метод и путь | Кто | Тело → ответ |
|---|---|---|
| `POST /imports` | взрослый | `{filename, content}` (текст CSV) → `201 Import` |
| `GET /imports` | взрослый | → `[Import]` без строк |
| `GET /imports/{id}` | взрослый | → `Import` со строками |
| `POST /imports/{id}/confirm` | взрослый | `{rows?: [{id, category?, include?}]}` → `200 Import` |
| `DELETE /imports/{id}` | взрослый | → `204` (только неподтверждённый) |

```ts
Import = {
  id; status: "pending" | "confirmed"; filename; createdAt; createdBy;
  totalRows; spendingRows; skippedIncome; duplicates; errors; imported: number;
  rows?: [{ id; rowNo; date; amount; description; mcc; suggestedCategory;
            duplicate: boolean; error: string | null; expenseId: string | null }]
}
```

## 11. Вход через ВТБ ID

**Зачем.** Путь к пилоту: вход через банк вместо токена устройства, участник связан с клиентом банка.

### Правила

- Стандартный OpenID Connect, Authorization Code + PKCE (S256), `state` и `nonce` одноразовые, живут 10 минут.
- Подпись `id_token` проверяется по JWKS провайдера; принимаются только RS256/ES256; проверяются `iss`, `aud`,
  `exp`, `iat`, `nonce`.
- Учётная запись провайдера (`sub`) привязывается к одному участнику. Вход по привязанному `sub` выдаёт обычную
  сессию. Если привязки нет — выдаётся одноразовый `linkToken` (10 минут), с которым можно создать семью
  или войти по приглашению — тогда новый участник сразу привязан.
- Для демо без банка есть встроенный тестовый провайдер (`OIDC_MOCK=true`): страница «войти как…» и подписанные
  токены. В бою он выключен.

### API

| Метод и путь | Кто | Тело → ответ |
|---|---|---|
| `GET /auth/oidc/config` | все | → `{enabled, providerName}` |
| `POST /auth/oidc/start` | все (для `link` — с токеном) | `{intent: "login" \| "link", redirectUri}` → `{authorizationUrl}` |
| `POST /auth/oidc/callback` | все | `{code, state}` → `Session` или `{status: "unlinked", linkToken}` или `{status: "linked"}` |
| `POST /families`, `POST /invites/{code}/join` | — | необязательное поле `oidcLinkToken` |
| `DELETE /me/oidc` | все | → `204` |

`redirectUri` должен входить в `OIDC_REDIRECT_URIS` — иначе `422`.
